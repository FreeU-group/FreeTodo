# 微信主动 OCR 适配设计

> 最后更新：2026-03-18
> 父文档：[1-1_感知流设计](./1-1_感知流设计.md)

---

## 一、背景

主动 OCR 是感知流中的事件驱动感知源（#4），专门针对微信/飞书等 IM 窗口做结构化聊天记录提取。微信作为用户使用频率最高的 IM，其 UI 在不同版本间会有布局微调、配色变化等差异。早期实现中大量使用**硬编码 RGB 值 + 极小容差**的方式做颜色匹配，导致每次微信更新后识别效果下降。

**本次改造目标**：将各环节从"精确匹配"改为"结构化特征 + 宽泛色彩空间"策略，使系统在微信改版后仍能稳定工作。

---

## 二、整体链路

```
窗口截图
  │
  ▼
[router.py] 进程名/窗口标题匹配 → 识别为 WECHAT
  │
  ▼
[wechat.py] 主题检测 + 标题栏分割 + 裁剪聊天区 ROI
  │
  ▼
[ocr_engine] 通用 OCR 引擎（RapidOCR / WinRT）识别文字
  │
  ▼
[wechat_message_parser.py] 气泡颜色+位置 → 说话人归属
                           时间戳识别 + 标准化
                           群聊昵称识别
                           → 输出：[私聊/群聊][名称] + [说话人] 消息
  │
  ▼
[sensor.py] 上报结构化文本 + metadata → 服务端
  │
  ▼
[orchestrator.py + dedupe.py] 微信消息行级去重 → 仅传递新消息给 LLM
```

## 四、各环节设计

### 4.1 窗口识别（router.py）

通过**进程名**优先匹配、**窗口标题**兜底匹配的两级策略识别微信窗口。

覆盖进程名：`weixin.exe`、`wechat.exe`、`wechatappex.exe`、`wechatbrowser.exe`、`wechat`、`微信`、`electronic-wechat`

标题关键词：`微信`、`wechat`（带边界判断防误匹配）

### 4.2 主题检测（wechat.py — detect_theme）

**设计思路**：使用区域平均亮度而非单像素精确 RGB 匹配。

- 采样区域：右下角 120×150 区域（避开气泡/头像，落在聊天背景上）
- 判断规则：平均亮度 < 100 → 深色主题，≥ 100 → 浅色主题
- 不依赖具体 RGB 值，微信换背景色不影响判断

**ThemeConfig 容差**：从 5 加宽至 30（用于基类颜色扫描兜底场景）

### 4.3 聊天区 ROI 提取（wechat.py — extract_chat_roi）

目标：裁掉左侧会话列表，只保留右侧聊天区。

**三级策略链**：

1. **结构化边缘检测**（`_find_sidebar_boundary`）
   - 在图像 15%~55% 宽度范围内，计算每列水平梯度的垂直总和
   - 梯度总和的峰值处即为侧栏-聊天区的分界线
   - 原理：该分界线是一条贯穿全高的一致性边缘，梯度信号远强于随机内容
   - 峰值需 > 均值 × 1.8 才采信

2. **背景色扫描兜底**（基类 `_find_bg_left_edge`）
   - 用主题背景色 + 宽容差（30）从右向左扫描
   - 在多个采样高度（h-80, h-120, h-160, h-200, h/2）取最小值

3. **固定比例兜底**
   - 若以上均失败或结果异常（< 10% 或 > 70% 宽度），取 35%

### 4.4 标题栏分割（wechat.py — find_title_divider_y）

检测标题栏与聊天区之间的细分隔线。

- 在顶部 25% 区域（水平 35%~90%）扫描行均亮度
- 寻找"亮度突变脉冲"（相邻行亮度差 > 8，且在 6px 窗口内出现反向变化）
- 失败时的 fallback 链：
  1. 固定比例 8%
  2. **OCR 文本兜底**：取右上方（图像上方 15%）最顶部的 OCR 文本行作为标题，其底部 y+2 作为分割线位置

### 4.5 气泡颜色与说话人归属（wechat_message_parser.py）

核心问题：判断每条 OCR 文本属于"我"还是"对方"。

**双策略分类**：

1. **HSV 色相检测**（主策略，版本无关）
   - 手动 RGB→HSV 转换（无 cv2 依赖）
   - 绿色判定条件：H ∈ [35, 85]（OpenCV 0-180 刻度），S ≥ 40，V ≥ 50
   - 右侧采样到绿色 → "我"；左侧采样到绿色 → "对方"
   - 原理：微信"我"的气泡始终为绿色系，色相在版本间稳定

2. **RGB 距离兜底**（旧逻辑，容差加宽至 40）
   - 用预设绿色/灰色 RGB 做欧氏距离比对
   - 作为 HSV 无法判断时的补充

3. **位置兜底**
   - 文字中心 x > 聊天区宽度 50% → "我"，否则 → "对方"

**多点采样策略**：

- 每侧采样 3 个 x 偏移量（5px、12px、20px）× 3 个 y 偏移量（-3、0、+3）
- 每组 3 个 y 值取均值作为一个采样点，共 3 个采样点
- 任一采样点命中即判定（`any()` 语义）

### 4.6 消息结构化解析（wechat_message_parser.py — parse_wechat_messages）

输入：聊天区图像 + OCR 原始结果 + 主题名

处理流程：

1. **标题提取**：分割线以上 OCR 行拼接为标题（含 OCR 文本兜底）
2. **聊天类型判断**：标题含 `(123)` 数字后缀 → 群聊，否则 → 私聊
3. **消息行过滤**：分割线以下、置信度 ≥ 0.5 的行，按 y 坐标排序
4. **逐行解析**：
   - 时间戳：居中 + 匹配时间正则 → 标准化为 `YYYY-MM-DD HH:MM`
   - 说话人：颜色分类（HSV → RGB → 位置三级）
   - 群聊昵称：短文本 + 小字号 + 与下条紧邻 → 识别为昵称行
5. **输出格式**：

```
[私聊][张三]
[时间] 2026-03-18 14:30
[张三] 明天的方案改好了吗
[我] 今晚发你
```

### 4.7 服务端消息级去重（dedupe.py + orchestrator.py）

- `WeChatMessageHistory`：维护已见消息行的滑动窗口
  - 按行解析 `[说话人] 内容` 格式
  - 归一化后做子串去重（A ⊆ B 视为已见）
  - 过滤噪声行（`发送`、`发送（` 等输入框残留）
  - TTL 1800s，最大 10000 行
- Orchestrator：全部已见 → 跳过（`DEDUPE_HIT`）；有新消息 → 替换 merged_text

## 五、泛化设计原则

| 原则 | 说明 |
|------|------|
| **色彩空间优于精确 RGB** | HSV 色相检测 "是不是绿色" 而非 "是不是 (87,190,71)" |
| **结构特征优于颜色匹配** | 侧栏分界用梯度峰值检测，不依赖具体背景色 |
| **亮度分类优于像素比对** | 主题检测用区域平均亮度，不比对单像素 RGB |
| **多级 fallback** | 每个环节至少有 2~3 级降级策略，任何一级失败都有兜底 |
| **多点采样** | 气泡颜色采样从 1 个点扩展到 9 个点（3 距离 × 3 纵向），抗噪声 |
| **宽容差** | 所有 RGB 容差从 5~25 统一加宽到 30~40 |
| **OCR 文本兜底** | 标题栏分割线找不到时，用最顶部 OCR 文本作为标题 |
